# App Folder: app/reset-password

> Enhanced folder documentation. Keep this file aligned with the folder workflow when behavior changes.

## Purpose

This folder owns the reset-password UI family. A user normally reaches it from a Resend email link that contains a one-time reset token.

## Route And Audience

- App route/group: `/reset-password`
- Folder path: `app/reset-password`
- Main audience/roles: `guest`
- Main interaction style: forms and client validation, toast feedback

## What Happens Here

- The actionable screen lives in `app/reset-password/[token]`.
- The token comes from the email link generated by `/api/forgot-password`; it is not fetched from session state.
- The reset form asks for a new password and confirmation, validates them with the shared strong-password rules, and posts the token plus new password fields to `/api/reset-password`.
- The API hashes the submitted token and compares it against the stored hash in MongoDB, so the raw token is never stored in the database.
- When the reset succeeds, the API hashes the new password with bcrypt, clears the reset token fields, and the UI shows success feedback.

- `app/reset-password/[token]/ResetPasswordForm.tsx`: functions/components: `ResetPasswordForm`, `onSubmit`; API calls: `/api/reset-password`; client component; form validation

## Reset Password Flow

1. The user clicks a Resend email link like `/reset-password/<token>`.
2. The route passes the token into `ResetPasswordForm`.
3. The form validates password strength and confirmation matching before submitting.
4. The API validates the token, checks expiry, blocks Google OAuth accounts, hashes the new password with bcrypt, and removes the token fields.
5. The user can then return to login with the new credentials password.

## Edge Cases And UX Rules

- Preserve route loading states so refreshes and slow network states look intentional.
- Preserve empty/error states so users are not left with blank screens.
- If forms exist, keep validation messages close to the field that failed.
- If this folder uses server data, keep cache invalidation/refetch behavior aligned with the owning API route.
- Expired or already-used links should fail cleanly because the API clears the token after a successful reset.
- Keep the token in the route only long enough to submit the reset request; never persist it in client storage.
- OAuth users should not be able to create a local password through this screen.

## How To Explain This In A Presentation

If someone asks what this folder does, say: this is the second half of password recovery. The email gives the user a one-time token, the frontend collects a strong new password, and the backend verifies the token/hash/expiry before replacing the stored password hash.
